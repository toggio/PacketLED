# LX.25 Protocol

Version 1, as implemented by PacketLED 1.0.1.

LX.25 is a point-to-point packet protocol for visible light, designed for two devices that each use a single LED to both transmit and receive. The name is a nod to AX.25, the link protocol of amateur Packet Radio, whose frame check sequence it reuses.

This document describes what goes over the light. A compatible implementation must transmit exactly this and accept it from the other side. How the receiver measures the light is up to the implementation; the approach used by PacketLED is described at the end for reference.

## 1. Physical layer

The medium is on-off keyed light: the LED is either on or off.

### Bit rate

Each bit lasts two equal halves (slots). The slot length, in microseconds, is

```
slot = floor(500000 / bitRate)
```

| Nominal rate | Slot | Bit |
|---|---|---|
| 256 bit/s | 1953 µs | 3906 µs |
| 512 bit/s | 976 µs | 1952 µs |
| 1024 bit/s | 488 µs | 976 µs |

The three rates above are the standard ones. PacketLED also accepts any integer rate from 256 to 1024. There is no rate negotiation: both sides must be set to the same rate.

The transmitter's timing should be accurate to a few microseconds within a frame. Clock differences of up to ±100 ppm between the two sides are tolerated.

### Bit coding

Bits are Manchester coded:

| Bit | First slot | Second slot |
|---|---|---|
| `0` | light | dark |
| `1` | dark | light |

Every byte is sent most significant bit first. This is not how AX.25 does it, which sends the least significant bit first.

## 2. Frame

A frame is sent as follows, starting from time `t0`:

| Part | Content | Timing |
|---|---|---|
| SYNC | LED on | from `t0` to `t0 + 20 ms` |
| GUARD | LED off | 3 ms |
| PREAMBLE | 16 bits, all `0` | starts at `t0 + 23 ms` |
| SFD | 1 byte, `0xA7` | |
| HEADER | 4 bytes | |
| PAYLOAD | 0 to 64 bytes | |
| FCS | 2 bytes | |

After the last bit the LED is switched off.

The bits from the PREAMBLE to the FCS form one continuous stream: bit `n` starts at `t0 + 23 ms + n × 2 × slot`.

### SYNC

20 ms of steady light. It tells the receiver that a frame is coming. A receiver should treat a light pulse from 17 to 35 ms long as a SYNC. Shorter or longer pulses are not frames. The lower limit keeps out mains interference: a 50 Hz half-wave lasts 10 ms.

The exception is a pulse that was already on when the receiver started listening, for example right after it finished transmitting. Its start was not seen, so its length is unknown, and it may be accepted from 5 ms up.

### PREAMBLE and SFD

The 16 `0` bits give the receiver a regular light/dark pattern to lock onto the bit timing. The start frame delimiter `0xA7` (`10100111`) marks where the header begins. A receiver that is unsure which preamble bit it is on can search for the SFD bit by bit.

### HEADER

| Byte | Field | Values |
|---|---|---|
| 0 | Type | `0x44` (`'D'`) data, `0x41` (`'A'`) acknowledgement |
| 1 | Session | see below |
| 2 | Sequence | see below |
| 3 | Length | payload length, 0 to 64; always 0 for an acknowledgement |

A receiver must reject a frame with an unknown type, a length above 64, or an acknowledgement with a non-zero length. The other type values are reserved for future versions.

### FCS

The frame check sequence is CRC-16/X.25, the same one used by AX.25 and HDLC. It is computed over the HEADER and the PAYLOAD (not the SFD):

- polynomial 0x1021, bit-reflected (0x8408);
- initial value 0xFFFF;
- final XOR 0xFFFF.

The check value for the ASCII string `123456789` is `0x906E`.

The FCS is sent low byte first. Each of its bytes is sent most significant bit first, like every other byte.

```c
uint16_t fcs16(const uint8_t *buf, size_t n) {
  uint16_t crc = 0xFFFF;
  for (size_t i = 0; i < n; ++i) {
    crc ^= buf[i];
    for (int b = 0; b < 8; ++b) crc = (crc & 1) ? (crc >> 1) ^ 0x8408 : crc >> 1;
  }
  return ~crc;
}
```

A frame with a wrong FCS must be discarded without any reply.

### Example frames

A data frame from session `0x5A`, sequence `0x01`, carrying `"Hi"`:

```
SFD      A7
HEADER   44 5A 01 02
PAYLOAD  48 69
FCS      5A 03          (FCS = 0x035A)
```

Its acknowledgement:

```
SFD      A7
HEADER   41 5A 01 00
FCS      93 1F          (FCS = 0x1F93)
```

## 3. Link layer

### Session and sequence

When a device starts, it picks a random session number and a random first sequence number. It then increments the sequence number, modulo 256, for every data frame it sends. A retransmission keeps the same sequence number.

The session number changes whenever the sender restarts. Together with the sequence number, it lets the receiver tell a retransmission from a new packet, even if the sender has rebooted and started counting again.

### Acknowledgements

A receiver that accepts a data frame answers with an acknowledgement:

- same session and sequence number as the data frame, that is, the **sender's** session, not its own;
- length 0, no payload;
- sent 20 ms after the end of the data frame.

A data frame is acknowledged even when the sender did not ask for confirmation. There is no flag for it in the frame. That sender simply ignores the reply.

A sender waiting for confirmation only accepts an acknowledgement that carries its own session and the sequence number it is waiting for. Any other acknowledgement is ignored.

### Spacing

A device waits at least 10 ms after the end of the last frame it received before it transmits. This gives the other side time to get back to listening, so that it sees the next SYNC from its start. An acknowledgement already waits 20 ms.

### Retransmission

A sender that wants confirmation:

1. sends the data frame;
2. waits up to 400 ms after the end of the frame for the matching acknowledgement;
3. if none arrives, waits a random 20 to 79 ms and sends the same frame again.

At most 3 transmissions are made in total. After that, the packet is reported as not delivered.

### Duplicates

The receiver remembers the session and sequence number of the last data frame it accepted. A data frame with the same session and sequence number is a duplicate: it is acknowledged again, because the previous acknowledgement may have been lost, but it is not delivered to the application a second time.

A receiver may also refuse a new data frame, for example because the previous one has not been read yet. It must then send no acknowledgement, so that the sender retransmits later.

### Collisions

There is no carrier sensing. If both sides transmit at the same time, the frames are lost and the random pause before each retransmission separates the two senders.

## 4. Receiver (informative)

This section describes how PacketLED receives. It is not part of the protocol: any method that decodes the frames above will do.

The LED is used as a sensor. It is reverse-biased, then its anode is left floating. Light hitting the junction charges it at a rate proportional to the light, and after a fixed integration time the ADC reads the voltage. PacketLED receives in five steps:

1. **Listening.** Integrations of at least 600 µs, compared with a dark level and a noise estimate that both follow the ambient light. A SYNC must rise above the dark level by at least 60 LSB and by three times the noise, so mains hum is not taken for light.
2. **SYNC.** When light is detected, the receiver picks an integration window for the frame that aims at a reading of about half the ADC range. It then waits for the light to go off.
3. **Phase.** On the preamble it takes eight pairs of readings. The two readings of a pair are half a bit apart, and each pair is shifted by an eighth of a bit from the previous one. The first harmonic of the eight differences gives the bit phase, and its magnitude the signal level.
4. **Bits.** Each bit is decided by comparing the readings of its two halves, so no threshold is needed.
5. **SFD.** The receiver reads bits until it finds `0xA7`, then reads the header, the payload and the FCS.

## 5. Constants

| Name | Value |
|---|---|
| SYNC length | 20 ms (accepted: 17 to 35 ms; from 5 ms if its start was not seen) |
| GUARD length | 3 ms |

| SFD | `0xA7` |
| Maximum payload | 64 bytes |
| Types | `0x44` data, `0x41` acknowledgement |
